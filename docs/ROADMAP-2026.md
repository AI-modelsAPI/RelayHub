# RelayHub 产品规划书（独立评审版）

> 评审日期：2026-09-20 · 评审方式：**仅读代码**（internal/ 131 个 Go 文件、19.5k 行、web/、tests/、Makefile），不参考任何现有文档或历史计划。
> 本文目的是跳出"补完 AxonHub 复刻"的思维，从"这是个什么产品、缺什么、能独有什 么"重新审视。

---

## 0. 一句话定位（从代码反推）

RelayHub = **本地优先的 AI 网关 + 渠道养号农场**。
它不只是"模型路由/聚合"（那是 AxonHub/One-API/New-API 的地盘），它独有的一极是 `internal/browser` + `internal/checkin`：**用真实浏览器自动给各渠道签到/养号，把"免费额度"变成可路由的资产**。这才是它和所有同类产品拉开差距的根。

```
独有资产（别人没有）          通用能力（大家都在卷）
┌─────────────────────┐      ┌──────────────────────┐
│ browser/cdp 真实点击 │      │ 多渠道/多Key/模型目录  │
│ checkin 定时签到养号 │  +   │ 协议转换 openai/anthropic│
│ clisync 接管本机CLI  │      │ 用量记录/导入导出/密钥库 │
└─────────────────────┘      └──────────────────────┘
        ↑ 护城河                    ↑ 已趋同质，卷不过头部
```

**结论：不要再把精力平均撒向"复刻 AxonHub 的 CRUD 页面"。通用 CRUD 你卷不过已成熟的 One-API 系。应把 80% 投入左侧护城河，20% 维持右侧"够用"。**

## 1. 现有功能盘点（代码实证）

| 模块 | 现状 | 评价 |
|---|---|---|
| `internal/router` | 协议+模型匹配、组（含 fallback 组）、priority/weight、health 感知选择 | 核心扎实，但策略只有 weighted/RR |

## 2. 需要改进的点（按痛点排序）

**A. 护城河没被产品化（最严重）**
- checkin 成果（Reward 字段）和"可路由额度"是**断开的**：签到拿到了额度，路由层并不知道这条渠道"今天有免费额度、优先用"。养号和路由两张皮，护城河白挖。
- 签到失败只落一条 CheckinRecord，没有"连续失败告警 / 自动降权 / 触发自愈"。

**B. 路由策略太弱**
- 只有 weighted/round-robin。**没有成本感知路由**（Model 已有 InputPrice/OutputPrice 字段却没人用）、**没有额度感知路由**、**没有延迟感知路由**。这是最容易做出差异化的地方。

**C. 用量数据"记了不用"**
- `usage` 端点只返回总 token/成功率/平均延迟。没有按渠道/模型的成本核算、没有趋势、没有"哪个渠道在白嫖/烧钱"。价格字段已存在，成本面板是顺手就能做的。

**D. 可观测性停留在"有日志"**
- 没有请求级追踪页、没有失败聚类、没有渠道健康时间线。HealthRecord 已存延迟，但没可视化。

**E. 多机/分发缺位**
- 纯单机 SQLite。养号农场天然想多机铺开（多 IP 抗封），但没有"主从/节点上报"能力。

## 3. 建议新增的功能（按差异化价值排序）

> 标 ★ 的为**同类（One-API/New-API/AxonHub/LiteLLM）没有或极弱**的独有功能。

### P0 — 把护城河闭环（最高优先）
1. **★ 额度感知路由（Quota-Aware Routing）**：checkin 拿到额度 → 写入 Channel.QuotaState → 路由选择器把"今日有免费额度"作为最高优先级因子。让"养号"直接转化为"省钱"。这是把两个独有模块焊死成飞轮的关键一环。
2. **★ 签到自愈（Checkin Self-Healing）**：连续 N 次失败 → 自动降权 + 标记 + 触发浏览器人工兜底提醒 + 可选自动重新登录。让农场无人值守。
3. **成本感知路由（Cost-Aware Routing）**：基于已存在的 InputPrice/OutputPrice，在同模型多渠道间优先走"折算单价最低 + 有免费额度"的渠道。配置 `strategy=cost_first`。

### P1 — 把数据变成洞察
4. **★ 免费额度账本（Free-Quota Ledger）**：每个渠道"今日签到获得 X 额度 / 已消耗 Y / 剩余 Z / 折合 $W"，首页一个"今日省下 $N"的大数字。养号农场的成就感来源，传播点。
5. **成本/用量面板**：按渠道/模型/时间维度的 token·成本·成功率·延迟图表（复用现有 RequestRecord，纯前端 + 聚合 SQL，不加依赖）。
6. **渠道健康时间线**：HealthRecord 可视化为每渠道的成功率/延迟热力图，一眼看出谁在掉链子。

### P2 — 农场规模化（独有方向的纵深）
7. **★ 多节点农场（Farm Peering）**：主节点下发渠道/凭据，从节点（不同 IP）执行签到并回传结果。抗封 + 扩量。现有 `peerAllowed` 已有雏形。
8. **签到策略市场**：adapter 已是插件式（agentrouter/gorouter/...5 个），开放" declarative 签到脚本（YAML DSL）"，让用户贡献新站点签到逻辑而不改 Go 代码。
9. **CLI 用量洞察**：clisync 已接管本机 CLI，顺势统计"Claude Code 本月烧了哪个模型多少 token"，给用户替代官方账单的视角。

### P3 — 体验与健壮（够用即可，别过度）
10. 请求级追踪页 + 失败聚类（按 ErrorClass 归类 Top N）。
11. 渠道批量操作/筛选补全（账本里的 Phase B/C 收尾，维持"够用"）。
12. WebSocket 实时推送网关事件（签到完成/渠道掉线）到前端，替代轮询。

## 4. 反路线图（明确不做什么）

- ❌ **不再继续像素级复刻 AxonHub 的渠道/模型 CRUD 页**。那是别人的战场，你追平也只是"又一个 One-API"。账本里 Phase B/C 收到"够用"即停。
- ❌ 不做多租户/计费/支付（偏离个人农场定位，复杂度爆炸）。
- ❌ 不上大型前端框架/构建链（保持 vanilla JS + embed，构建简单是优势）。
- ❌ 不引入重型依赖（现仅 sqlite+yaml+uuid+crypto，干净，保持）。

## 6. 为什么这样排

1. **M1 把两个独有模块焊成飞轮**——投入最小（字段和选择器都在），差异化收益最大，做完产品就有了别人抄不走的故事。
2. **M2 让用户"看见"省下的钱**——养号农场没有正反馈就没人用，账本是留存和传播的关键。
3. **M3 才扩规模**——单农场闭环成立后再多机，避免过早分布式。
4. **M4 收尾通用能力**——最后补，且只到"够用"。

核心一句话：**别再追 AxonHub 的页面，把"自动养号 → 额度 → 智能路由 → 省钱"这条别人没有的链路做成飞轮。**
