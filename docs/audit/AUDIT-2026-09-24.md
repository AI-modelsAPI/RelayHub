### 兼容性变更（升级说明）

- HTTP 代理不再接受 origin-form 请求（正向代理本来就只应接受 absolute-form）。两个代理永远拒绝 RelayHub 自身的端口和云元数据地址。
- `http_proxy_target_policy` / `socks5_target_policy` 现在真正生效；拼写错误会阻止启动。
- 网关不再转发 `Accept-Encoding`、`Origin`/`Referer`/`Sec-*`、`OpenAI-Organization/Project`，也不再跟随上游重定向。
- `cli-sync` 的 `base_url` 只能指向本机网关。
- 修改渠道 `base_url` 使 origin 变化后，需要重新录入该渠道的 Key（旧 Key 会被锁定，测试时返回 409）。
- 带密码的导出包格式为 v3；旧版 RelayHub 无法导入 v3 包。
- **管理 API 默认要求令牌（F4）**，读取接口也不例外。首次启动会生成 `<data-dir>/management.token`；直接调用管理 API 的脚本需要带上 `Authorization: Bearer $(cat <data-dir>/management.token)`。控制台用启动日志或 `relayhub pair` 打印的一次性链接配对；`relayhub mcp` 和 macOS 桌面端会自动读取令牌。`/api/v1/health`、`/healthz` 仍然公开。设置 `management_auth: off`（或 `RELAYHUB_MANAGEMENT_AUTH=off`）可恢复旧行为，但它与 `management_token` 同时设置会阻止启动。
- 设置 `proxy_username`/`proxy_password` 后，本地代理的客户端需要携带认证；只设置其中一个会阻止启动。
- 渠道 `custom_headers` 中值为空的条目，现在表示“删除该请求头”（以前会发送一个空值头）。名字以 `*` 结尾时按前缀删除。
- 浏览器签到改用 `--remote-debugging-pipe`，不再监听 DevTools 端口。
- 已上线渠道在后台同步中新声明的、其他渠道已提供的模型，默认处于禁用状态。
- `master_key_store: keychain` 只能在 macOS 上使用，其他平台选择它会阻止启动。

| 严重度 | 数量 | 编号 |

**实测复现（PoC）的有 10 项**：F1、F2(c)、F3（HTTP 和 SOCKS5 两种代理都能复现）、F5、F6、F8、F9、F12、F14、F20，另外 F19 用实际数据目录验证过。

**最该先修的 5 项（建议本周内）：**

1. **F3 本地代理可以直接访问管理 API**：`curl -x http://127.0.0.1:8787 http://127.0.0.1:8790/api/v1/keys -d '{}'` 就能铸出一把完整的 `rh_` 网关密钥。SOCKS5 也一样。浏览器边界（Sec-Fetch-Site / Host 校验）被完全绕开。
2. **F1 代理自环 DoS**：只要一个 `GET http://127.0.0.1:8787/`（网页里放一个 `<img>` 就能触发），4 秒内 fd 被打满到 4096。**网关、管理 API、代理全部停止响应，60 秒后仍未恢复，只能重启。**
3. **F12 修改身份时会静默清掉渠道代理**：`PATCH /api/v1/identity/{id}` 只改 UA，结果渠道的 `proxy_url` 被置空，**这个渠道从此直连，暴露真实 IP**。这直接违背产品“统一出口”的核心承诺。
4. **F8 转发客户端的 `Accept-Encoding` 导致非流式请求失败**：Python httpx / requests、Node fetch 等 SDK 默认都会带 `Accept-Encoding: gzip`。只要上游愿意压缩（套了 nginx / Cloudflare 的中转站基本都会），网关就会返回 502 “malformed upstream JSON”，还把渠道记为不健康。
5. **F5 + F14 “只写”密钥能被外带，CLI 能被劫持**：把渠道 `base_url` 改成攻击者主机后调用 `/channels/test`，真实上游 Key 会以 Bearer 形式发过去。`cli-sync` 也可以把 Claude Code / Codex 指到任意地址。

> **一条完整攻击链**（Docker bridge 部署或 LAN 绑定）：同网段任一主机 → 无认证的 8787 代理（F2）→ 访问未发布的管理 API（F3）→ 读配置、铸网关 Key → 改 `base_url` + `/channels/test` 外带所有上游 Key（F5）→ `cli-sync` 把用户的 Claude Code 指到攻击者服务器（F14）→ 拿到后续所有 prompt。整条链**没有任何一步需要凭据**。

## 2. 详细发现

> 复现环境：用 HEAD 编译出二进制 `relayhub -full-stack`，端口分别为 管理 18790 / HTTP 代理 18787 / SOCKS5 18788 / 网关 18789，`ulimit -n 4096`。下面命令里的端口换成默认的 8787/8788/8789/8790 效果相同。

### F1 🟠 High —— HTTP 代理自环 DoS（网页即可触发，整个进程都会挂掉）

**位置**：`internal/proxy/http_proxy.go:184-187`

```go
authority := r.URL.Host
if authority == "" {
    authority = r.Host        // ← origin-form 请求（GET / HTTP/1.1）回退到 Host 头
}
```

当请求不是代理格式（absolute-form），而是普通的 origin-form 时，代码会拿 `Host` 头作为上游地址。直接访问代理端口时，`Host` 正好就是代理自己（`127.0.0.1:8787`），于是代理连接自己、再次收到同样的请求、再连接自己……形成无限递归。每一层占用 2 个 fd，永远不会释放。

**PoC（实测）**：
```bash
curl -m 8 http://127.0.0.1:8787/
# 进程 fd：16 → 4096（4 秒内）
# 日志出现 71 条 "accept4: too many open files"
# t+5s / t+30s / t+60s：管理 API 与网关都无响应（HTTP 000），进程还活着但不可用 → 只能重启
```

**影响**：
- 任意网页中的 `<img src="http://127.0.0.1:8787/">` 就能触发。浏览器不需要任何权限，Sec-Fetch 类防护也管不到代理端口。
- 由于**三个平面共享同一个进程的 fd 表**，代理被打爆后，网关（Claude Code / Cursor 的所有请求）和管理 UI 会一起瘫痪。
- macOS 上 launchd 默认 fd 软上限只有 256，触发会更快。

**修复**：
1. origin-form 请求直接返回 `400`（正向代理本来就不应该接受 origin-form），**不要回退到 `r.Host`**。

**位置**：F2 的开放代理，加上管理 API 的浏览器边界设计（`internal/api/browser_boundary.go`）

**PoC（实测，HTTP 和 SOCKS5 都能复现）**：

**修复（任选其一，建议组合）**：
1. 代理的目标策略**永远拒绝本进程的监听地址**（在 F1 修复第 2 点的基础上实现）。
2. 管理 API 默认要求 token（见 F4），不再把“来自回环”当作可信。

### F8 🟠 High —— 网关透传客户端请求头：`Accept-Encoding` 让非流式请求失败，还会泄露客户端指纹

**位置**：`internal/gateway/gateway.go:657-690`（`requestHeaders`）、`:497`

```go
h := r.Header.Clone()   // 全量复制客户端请求头
h.Del("Authorization"); h.Del("x-api-key"); h.Del("Cookie") ... // 只删了少数几个
```

1. **功能性故障**：Python httpx / requests、Node undici 等 SDK 默认都会带 `Accept-Encoding: gzip, deflate`（curl 要加 `--compressed` 才会带）。网关把这个头原样转发后，Go 的 Transport 就**不会再自动解压**（只有 Transport 自己加上的 `Accept-Encoding` 才会透明解压）。上游返回 gzip 字节，网关按 JSON 解析失败。
   **PoC（实测，`httptest` 桩上游）**：同一个非流式请求，带 `Accept-Encoding: gzip, deflate` 时返回 **502 `provider_protocol` "malformed upstream JSON response"**，并记一次渠道健康失败；去掉这个头则返回 200。
   后果是一个完全健康的渠道会被误判下线，还可能触发熔断和级联失败。
2. **隐私 / 指纹**：`X-Stainless-OS`、`X-Stainless-Arch`、`X-Stainless-Runtime-Version`、SDK 的 `User-Agent`、`OpenAI-Organization`、`OpenAI-Project`、`anthropic-beta` 等都会被原样发给第三方中转站。这与“统一出口 / 身份隔离”的产品定位相矛盾：出口 IP 统一了，指纹却每个客户端各不相同。
3. `:497` 对非流式响应用 `io.LimitReader(…, 16<<20)` **静默截断**，大响应（例如图像 base64）会被误报为 “malformed JSON”。请求侧 `:270` 同样是静默截断。

**修复**：
- 改为**白名单**转发：按协议只保留 `Content-Type`、`Accept`、`anthropic-version`、`anthropic-beta`（可配置）等必要头；显式删除 `Accept-Encoding`，让 Transport 自己管理压缩。
- 增加“身份头配置”：每个渠道选择 `minimal`（白名单最小化）、`passthrough`（兼容）或 `profile`（统一成一套固定的头），见 §5 A4。
- 超过上限时返回明确的 413 / 502 `response_too_large`，不要静默截断。

### F9 🟡 Medium —— 上游重定向不受控：SSRF + 响应形态不校验

**位置**：`internal/egress/egress.go`（所有 client 都没有 `CheckRedirect`）、网关非流式响应路径

- 上游返回 `302 Location: http://127.0.0.1:8790/api/v1/settings`（或任意内网地址）时，网关会**跟随重定向发起 GET**，并把内网响应当作上游的 200 正文返回给客户端。
  **PoC（实测，`httptest`）**：桩上游返回 302 指向第二个内网桩，客户端收到的是 **200 + 内网桩的正文**。
- 网关**不校验 200 响应的形态**（Content-Type、JSON schema），所以 HTML 验证页、内网页面、余额不足页都会被当作成功透传。
- 307 / 308 时 `GetBody == nil`，POST 正文不会重放，上游收到空请求；跨主机重定向时，Go 只会剥离 `Authorization` / `Cookie`，**不会剥离 `x-api-key`**（Anthropic 协议的 Key 头），存在跨站泄露 Key 的风险。

**修复**：网关和探测 client 统一设置 `CheckRedirect: func(...) error { return http.ErrUseLastResponse }`（API 流量本来就不应该跟随重定向），把 3xx 视为上游错误；非流式响应校验 `Content-Type` 为 `application/json`，并用 `json.Valid` 检查正文；流式响应校验 `text/event-stream`。

  - `RELAYHUB_MGMT` 写的是**网关端口**，不是管理端口；而且 `cmd/relayhub/mcp.go` **根本不读这个变量**（只读 `RELAYHUB_MANAGEMENT_TOKEN`）。结果使用非默认端口时，MCP 必然连不上。
  - `command: "relayhub"` 依赖 PATH：PATH 里排在前面的同名可执行文件会被 Claude Code 当成 MCP 服务器启动（桌面版的二进制名是 `relayhub-core`，并不在 PATH 里）。
- Codex 的 TOML 重写会丢失用户注释（体验问题，这里一并记录）。
- 待确认：Claude Code 用 `claude mcp add --scope user` 添加的用户级 MCP 实际存放在 `~/.claude.json`，而不是 `~/.claude/settings.json`（见 [anthropics/claude-code#37165](https://github.com/anthropics/claude-code/issues/37165)）。建议用真实的 Claude Code 验证一下写入 `settings.json` 的 `mcpServers` 是否会被加载。

**修复**：`base_url` 只允许本实例网关地址（服务端自己算出来，不从请求里读），最多允许用户显式确认过的自定义地址；MCP 条目写入**绝对路径**（`os.Executable()`），环境变量名与 `mcp.go` 保持一致，并指向管理端口；每次 apply 在 UI 中展示 diff 并要求二次确认。

### F15 🟡 Medium —— 签到用 Chrome 暴露 CDP 端口，本地任意进程可以接管会话

**位置**：`internal/browser/launch.go:150-181`、`internal/browser/executor.go:63`（`findFreePort`）

- 启动参数是 `--remote-debugging-port=<随机端口>`，监听在回环 TCP 上。签到窗口存在期间，**任何本地进程或同机其他用户**都可以连上 DevTools，执行 `Network.getAllCookies` 导出各中转站的登录态，或者直接操控页面。
- `findFreePort` 先 `Listen(:0)` 拿到端口再关闭，然后交给 Chrome，中间存在 TOCTOU 窗口：恶意进程可以抢先占住这个端口，冒充 CDP 端点，反过来控制 RelayHub 的签到逻辑（诱导它点击或填写内容）。
- `--password-store=basic --use-mock-keychain` 让 profile 里的 cookie 只用固定口令加密，基本相当于明文落盘。

**修复**：改用 `--remote-debugging-pipe`（fd 3/4 通信，不开任何端口）；profile 目录保持 0700；把 cookie 的留存范围限制到目标站点，签到结束后清除其他域的数据；如果必须使用 TCP，也要校验 `/json/version` 返回的 `webSocketDebuggerUrl` 与启动的子进程是否匹配。

### F16 🔵 Low —— 适配器跨域重定向时会带上身份头

**位置**：`internal/adapter/base.go:296-345`（`CallWithAuth`）

Go 在跨域重定向时会自动剥离 `Authorization` 和 `Cookie`（这部分已确认没问题），但 `X-User-Id`（new-api 的用户 ID）和渠道的 `custom_headers`（可能含私有鉴权头，见 F10）会原样跟随到新域名。

**修复**：与 F9 一样禁止跟随重定向，或者在 `CheckRedirect` 里遇到跨 origin 时清除所有非白名单头。

### F17 🔵 Low —— 导出包“防篡改”可以绕过，并且会泄露口令验证器

**位置**：`internal/export/format.go:87-101`、`internal/export/import.go:21-40,121-139`、`internal/export/crypto.go:18-20`

1. **降级绕过**：导入时，`Version == 1 && !HasSecrets` 的包只校验**无密钥的 sha256**。攻击者可以拿到任意 v2 包（或者自己构造），把版本号改成 1，改掉 `base_url` 等字段后重新计算 sha256，导入端会认为包“完整无篡改”。“社区分享配置包”这类场景会直接受影响。
2. **固定盐**：V2 的 HMAC 密钥是 `Argon2id(password, "relayhub-export-checksum-v2")`，盐是公开常量，所以攻击者可以**对所有用户预计算一张常见口令表**。
3. **口令验证器外泄**：不含秘密的包也带着这个 HMAC，拿到包的人可以**离线爆破导出口令**（用户往往会复用口令）。
4. Argon2id 参数 `t=1, m=64 MiB` 低于 RFC 9106 的两档推荐值（`t=1, m=2 GiB` 或 `t=3, m=64 MiB`）。

**修复**：导入时拒绝 v1（或者 v1 只允许在明确的 `--legacy` 开关下使用，并显示“未验证”）；HMAC 的盐使用包内随机 salt（和加密共用 KDF 输出，再用 HKDF 拆分成 enc / mac 两把子密钥）；不含秘密的包改用签名，或者干脆不带 MAC；Argon2 调到 `t=3`。

### F18 🔵 Low —— 主密钥和密文放在一起，备份会同时带走

**位置**：`internal/secrets/keyring.go`（`<data-dir>/master.key`）、`desktop/macos/KeychainStore.swift`（仍未接线，RH-27）

`master.key`（0600，权限校验做得很好）和 `relayhub.db` 在同一目录下。macOS 默认路径位于 `~/Library/Application Support/relayhub`，会被 **Time Machine / 各种同步盘 / 整机备份一起带走**，拿到备份就等于拿到明文。“AES-256-GCM 加密存储”在这种威胁模型下几乎不提供额外保护。

**修复**：macOS 上把主密钥放进 Keychain（`kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`，不随备份迁移），Linux 上用 libsecret 或 TPM；实在做不到，至少对 `master.key` 设置 `tmutil addexclusion` / `NSURLIsExcludedFromBackupKey`，并在文档中说明风险。

### F19 🟡 Medium —— 数据目录权限不会被收紧，DB 实测 0644

**位置**：`internal/app/wiring.go:85`（`os.MkdirAll(absDataDir, 0700)`）、`internal/storage/db.go:67`

`MkdirAll` 只对**新建**的目录生效。如果目录已经存在（Docker 镜像里 `mkdir /data` 创建的是 755；用户手动创建或从旧版本升级），就沿用原来的宽权限。SQLite 按 umask 创建 `relayhub.db` / `-wal` / `-shm` 文件。
**实测**：预先创建好的数据目录中，`relayhub.db` 是 **0644**（其他用户可读），`master.key` 是 0600（这部分没问题）。

DB 里**明文**存放着：代理 URL（含用户名和密码）、`custom_headers`（可能含鉴权头，见 F10）、请求元数据、`rh_` 密钥哈希等。

**修复**：启动时对数据目录执行 `Chmod(0700)`（如果属主不是当前用户，就拒绝启动并给出提示）；打开 DB 前设置 `umask(0077)`，或者主动 `Chmod(0600)` DB、WAL、SHM 文件；代理密码和敏感头迁移到 SecretStore。

### F20 🟡 Medium —— 通知失败时，日志里泄露 Telegram bot token 和 Bark 设备密钥

**位置**：`internal/notify/notify.go:172`（`…/bot<TOKEN>/sendMessage`）、`:334-345`（把错误交给 `Logf`）、`internal/app/wiring.go:110`（`Logf = log.Printf`，不经过脱敏）

Go 的 `*url.Error` 会把**完整 URL** 放进错误信息里。**实测**：
```
Post "https://…/bot123456789:AAHdqTcv…/sendMessage": dial tcp …: connect: connection refused
```

网络抖动、DNS 失败、Telegram 在部分地区被墙等情况下，bot token 就会进入 stderr、Docker 日志或 macOS 日志文件。Bark 的 URL 路径（`https://api.day.app/<device_key>/…`）也一样。另外，现有脱敏正则 `apiPattern` 不匹配 `\d+:[A-Za-z0-9_-]{35}` 这种 bot token 格式。此外，`config.json` 里的 bot token 本身也是明文（建议迁移到 SecretStore）。

**修复**：Send 失败时只记录 `host + 状态 / 错误类别`，用 `errors.As(&url.Error)` 取出 `Err` 再格式化；脱敏器补充 Telegram token 正则和 URL path 脱敏；log 统一走脱敏 logger。

## 5. 产品与功能建议（超出 `strategy-review-2026-09-21.md` §7 的部分）

> §7 已经规划了：一行安装与首跑向导、`route explain` CLI、首页“一个数字”、出口探针与 429 换出口、声明式 DSL 扩展、隐私诊断包、`web/` 单一来源。下面的建议**不与这些重复**。

### 核心判断：RelayHub 真正的护城河是“信任边界”

Metapi、All-API-Hub、CLIProxyAPI、CC Switch 都在做“聚合”和“切换”。而 RelayHub 实际所处的位置是：

> **高价值的本地开发工具（Claude Code / Codex / Cursor，带着代码和 prompt）** ⇄ **RelayHub** ⇄ **半可信的第三方中转站（随时可能掺水、跑路、被攻陷）**

这次审计发现的问题，几乎全部出在这条边界上：中转站能冒名（F6）、能重定向（F9）、能收集指纹（F8）；本地侧能被绕过（F3）、被劫持（F14）。所以建议把**“中转站是半可信第三方”写进设计原则**，并把相关能力做成产品卖点，而不是只当作安全补丁。这也是竞品都没有占住的位置。

### A. 安全架构：把审计修复变成卖点

**A1. 管理平面不再占用 TCP 端口。**
- 桌面版的管理 API 改走 Unix Domain Socket（权限 0600）。
- WKWebView 通过 `WKURLSchemeHandler`（`relayhub://`）访问管理 API，CLI 和 MCP 也走 UDS。
- 只有用户主动开启“浏览器访问”时才监听 TCP，而且必须先用 token 配对。
- 这样可以从根上消除 F3 / F4 / F11 这一类问题。“没有管理端口”本身也是一个很好的宣传点。

**A2. 密钥绑定 origin，并记录密钥去向。**
- 每把上游 Key 在录入时绑定 `scheme://host:port`。origin 一变，Key 自动锁定，必须重新输入（F5 的结构性修复）。
- 另外维护一本**“密钥去向账本”**：每次发送 Key 时，记录 `(origin, 用途, 时间)`。
- UI 上可以直接看到“这把 Key 曾经发往哪些主机”。任何异常主机都一目了然，用户的信任感会很强。

**A3. 出口完整性守护（Egress Integrity Guard，相当于 VPN 的 kill switch）。**
- 每个渠道可以声明一份**出口契约**：必须使用哪个代理、期望的国家 / ASN、是否必须远程解析 DNS（`socks5h`）。
- 每次冷启动和每 N 分钟做一次断言。
- 违反契约时隔离该渠道，**永远不降级为直连**。
- UI 上的“出口”列从“显示 IP”升级为“契约是否满足 ✅ / ❌”。
- F12、F13 这类问题今后会被自动拦截。
- 它与 §7.4 的“出口探针”不同：§7.4 是展示信息，这里是强制执行。

**A4. 请求头卫生配置。**
- 每个渠道三选一：`minimal`（白名单）、`passthrough`、`profile`（统一成一套固定的头）。
- 默认使用 `minimal`，不再把 `X-Stainless-*`、`OpenAI-Organization` 等头送给第三方（F8）。
- 请求日志里显示“实际发出的头”，经过脱敏，方便排查。

**A5. 代理默认鉴权，并且按工具分配凭据。**
- 为每个工具生成一对代理凭据，例如 `cursor:xxx@127.0.0.1:8787`。
- 这样一来，代理流量就能**归属到具体工具**，可以分别统计，也可以按工具配置出口策略（例如 Cursor 只允许访问 `*.openai.com`）。
- 顺带修复 F2。

**A6. 首次运行的安全自检（“体检”页）。**
- 启动时自动检查以下项目，并给出一键修复：
  - 数据目录权限（F19）；
  - 代理是否绑定到了非回环地址；
  - 是否在云主机上、元数据地址是否可达（F2）；
  - 通知 token 是否明文保存（F20）；
  - `master.key` 是否在备份范围内（F18）。
- 竞品都没有这个功能。它的成本很低，却很能体现“这个工具是懂安全的”。

### B. 治理半可信中转站（差异化的核心）

**B1. 掺水 / 降智检测：模型真实性探针。**
这是中转站生态里最大的痛点：声称提供 Opus，实际给的是便宜模型。建议定期发送少量 canary 请求，为每个渠道计算“真实度”分数。可用的信号有：
- **已知答案题**：答案在各模型上稳定，但不同模型之间有区分度。
- **分词器指纹**：对同一段输入，不同模型家族上报的 `usage.prompt_tokens` 有稳定差异。本地先算出期望值，与上游上报值对比即可。
- **响应里的 `model` 字段**：网关已经在 `streamMeta.UpstreamModel` 中记录了这个字段。与请求的模型不一致时直接告警，这一步几乎不需要额外成本。
- **能力探测**：检查 tool use、vision、长上下文、`thinking` 等能力是否真的可用。

分数进入路由权重，分数低的渠道自动降权。

**B2. 计费对账：发现倍率变动和多扣费。**
- new-api 系站点的用量和日志接口，适配器本来就在读。把本地统计的 token 数（请求加响应）与站点实际扣除的额度对比，就能算出每个渠道的**有效单价**（美元 / 百万 token）。
- 站点偷偷调倍率或出现多扣费时，立即告警。
- 路由可以按“有效单价”而不是“标称价格”排序。
- “今日省下 $Y”（§7.3）也会因此从估算变成真实数据。

**B3. 模型目录的来源和审批（F6 的产品化）。**
- 上游新出现的模型先进入“待审”区，UI 显示“这个站点新增了 12 个模型”。
- 用户点击批准或映射后，模型才能占用全局名称。
- 热门名称受保护：`claude-*`、`gpt-*` 默认只能由标记为“可信”的渠道认领。
- 每次同步保留快照，支持**一键撤销上一次同步**。

**B4. 流式“首包前透明重试”。**
- 现状：`writeSSE` 一收到上游 200 就立刻 `WriteHeader(200)`（`stream.go:31-36`）。如果上游随后第一条事件就是错误，比如 new-api 常见的 200 + `data: {"error":…}`、Cloudflare 验证页、余额不足页，这个错误会直接交给客户端，**无法再切换渠道**。
- 建议：先缓冲，直到收到**第一个有效的 delta**（或者等满 N 毫秒）才提交响应头。在此之前出现的错误、非 SSE 内容或 HTML，都透明地切到下一个渠道。
- 对用户来说，效果就是 Claude Code 里的报错大幅减少。这是体验上最能直接感知的一项改进，实现成本却不高。

**B5. 渠道健康的语义化。**
- 把“HTTP 200 但内容不对”（HTML、空响应、JSON 里带 error 字段，也就是 F9 的形态问题）计为软失败。
- 熔断器增加 half-open 状态，用低成本请求探活，例如 `max_tokens=1`。

**B6. 中转站信誉的社区共享（可选，隐私优先）。**
- 在用户明确同意的前提下，匿名上报站点的可用率和真实度分数，只上报域名的哈希。
- 以此形成一份社区“跑路 / 掺水预警”列表。
- 这是网络效应型的护城河，竞品很难复制。

### C. 多工具与多用户治理

**C1. 本地 Key 升级为带策略的 Key。**
- 现状：`auth/local_keys.go` 只存 `id → sha256`，没有名称、用途、过期时间、预算或模型范围。
- 建议给每把 Key 加上以下属性：
  - 名称或所属工具（Cursor、Claude Code、脚本……）；
  - 允许的模型；
  - 每日或每月预算（美元）；
  - 速率限制；
  - 过期时间；
  - 最后使用时间和来源。
- 效果是可以做到“给每个工具发一把钥匙，Cursor 每天最多 $3，脚本只能用 haiku”。这正是多工具并用的开发者最需要的能力。

**C2. 按工具归因的用量看板。**
- 结合 C1 和 A5，用量可以按工具拆分，例如“今天 Claude Code 花了 $4.2，Cursor 花了 $0.8”。

**C3. 配置即代码。**
- 提供 `relayhub plan -f relayhub.yaml` 和 `relayhub apply`：先展示差异，再执行变更，并能检测漂移。
- 配置文件里的秘密用引用表示，例如 `keychain://`、`op://`（1Password）、`env://`，**文件本身不含任何秘密**，可以放心提交到 dotfiles 仓库。
- 与现有的导入导出（F17）相比，这是更适合开发者的一条路。

### D. 工程与交付

**D1. 签名、公证与可验证的发布。**
- 现状：`release.yml` 只构建 DMG，作为 artifact 保留 7 天。没有 GitHub Release，没有代码签名和公证，也没有校验和、SBOM 或来源证明。
- 未签名的 DMG 会让用户习惯性地绕过 Gatekeeper，这对一个经手 API Key 的工具来说代价很高。
- 建议补齐以下几项：
  - Developer ID 签名；
  - `notarytool` 公证；
  - `SHA256SUMS` 校验和；
  - `actions/attest-build-provenance` 来源证明；
  - Homebrew cask。
- 另外，actions 应该 pin 到具体 SHA，`govulncheck` 也要固定版本。

**D2. 可观测性。**
- 提供 Prometheus `/metrics` 端点（仅在管理面提供），导出按渠道统计的延迟、错误类别、首 token 时间和熔断状态。
- 可选输出 OTel trace，方便接入 Grafana。
- 目前代码中没有任何 metrics 导出。

**D3. 回归测试护栏（对应本次发现）。**
- **路由表鉴权测试**：遍历所有注册路径，断言未带 token 时返回 401（F11）。
- **代理自环测试**：请求 `GET http://<proxy>/` 必须返回 400 或 508（F1）。
- **身份 PATCH 测试**：只改 UA 时，`proxy_url` 必须保持不变（F12）。
- **网关压缩测试**：请求带 `Accept-Encoding: gzip` 时，非流式请求仍返回 200（F8）。
- **重定向测试**：上游返回 302 时，网关不应跟随（F9）。
- **配置落地测试**：在 `config.json` 里设置的策略值，必须体现在启动日志中（F2）。

**D4. 按平面隔离资源。**
- 代理、网关、管理三个平面分别设置连接上限，互不拖累（F1 的纵深防御）。
- 长期可以考虑把代理拆到独立进程中运行。

```go
// POC-A: client Accept-Encoding is forwarded; upstream gzips; gateway parses gzip as JSON.
func TestAuditPOC_AcceptEncodingBreaksNonStream(t *testing.T) {
	up := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		t.Logf("upstream saw Accept-Encoding=%q X-Stainless-Os=%q Origin=%q", r.Header.Get("Accept-Encoding"), r.Header.Get("X-Stainless-Os"), r.Header.Get("Origin"))
		body := []byte(`{"id":"x","object":"chat.completion","choices":[{"index":0,"message":{"role":"assistant","content":"ok"},"finish_reason":"stop"}]}`)
		w.Header().Set("Content-Type", "application/json")
		if strings.Contains(r.Header.Get("Accept-Encoding"), "gzip") {
			w.Header().Set("Content-Encoding", "gzip")
			gz := gzip.NewWriter(w)
			_, _ = gz.Write(body)
			_ = gz.Close()
			return
		}
		_, _ = w.Write(body)
	}))
	defer up.Close()
	gw := auditGW(up.URL)
	for _, ae := range []string{"", "gzip, deflate"} {
		req, _ := http.NewRequest(http.MethodPost, "/v1/chat/completions", bytes.NewReader([]byte(`{"model":"m1","messages":[{"role":"user","content":"hi"}]}`)))
		req.Header.Set("Content-Type", "application/json")
		req.Header.Set("X-Stainless-Os", "MacOS")
		if ae != "" {
			req.Header.Set("Accept-Encoding", ae)
		}
		w := httptest.NewRecorder()
		gw.ServeHTTP(w, req)
		t.Logf("client Accept-Encoding=%q -> gateway status %d body=%.120s", ae, w.Code, w.Body.String())
	}
}

// POC-B: upstream 302 redirect makes the gateway issue a GET to an arbitrary (internal) URL.
func TestAuditPOC_RedirectSSRF(t *testing.T) {
	var internalHit string
	internal := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		internalHit = r.Method + " " + r.URL.String() + " auth=" + r.Header.Get("Authorization") + " xkey=" + r.Header.Get("X-Api-Key")
		w.Header().Set("Content-Type", "application/json")
		_, _ = w.Write([]byte(`{"secret_internal":"management-data"}`))
	}))
	defer internal.Close()
	evil := httptest.NewServer(http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
		http.Redirect(w, r, internal.URL+"/api/v1/settings", http.StatusFound)
	}))
	defer evil.Close()
	gw := auditGW(evil.URL)
	req, _ := http.NewRequest(http.MethodPost, "/v1/chat/completions", bytes.NewReader([]byte(`{"model":"m1","messages":[{"role":"user","content":"hi"}]}`)))
	w := httptest.NewRecorder()
	gw.ServeHTTP(w, req)
	t.Logf("internal server hit: %q; gateway returned %d %.100s", internalHit, w.Code, w.Body.String())
}
```
