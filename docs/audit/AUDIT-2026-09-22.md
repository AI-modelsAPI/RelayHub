## 3. P1 — 高优先级问题

### P1-1 数据列漂移：`request_records` 迁移 008 的 5 个新列只写不读
`repository.go:783-786` `CreateRequestRecord` INSERT 17 列（含 `ttft_ms/cache_read_tokens/cache_write_tokens/finish_reason/upstream_model`）；但 `scanRequest`/`GetRequestRecord`/`ListRequestRecords`（`repository.go:793-831`）SELECT 只有 12 列。**读出路径永远丢失这 5 个字段** → `usage/summary` 的 `cache_hit_ratio`（就算注册了也）恒为 0、`routes/explain`/`mcp explain_last` 的 finish_reason/ttft 恒空、channelStats 用不上 TTFT。修复：SELECT 补齐列名与 scan 目标。

### P1-2 `request_records` 无分页无保留策略，三个端点全表扫描
`ListRequestRecords` 无 `LIMIT`（`repository.go:816`），表随每个网关请求增长且无清理任务（grep 全仓无 `DELETE FROM request_records`/retention）。`/api/v1/usage`、`/api/v1/channels/stats`（内存过滤 channel_id）、`usageSummary`、MCP `quota_status`/`explain_last` 每次都把**全表**载入内存聚合。前端每 15 秒轮询一次 `/api/v1/usage`，随时间推移管理面确定性变慢直至不可用。修复：SQL 侧聚合（`GROUP BY`/`SUM`/`COUNT`）+ `LIMIT ?` 参数 + 定期 prune（如保留 7 天/10 万行）。

### P1-3 加权组故障转移不完整
`resolve()` 中 `selectGroupModel`（`selector.go:273`）内部的 `r.candidates(protocol, model, d, filter, now, req)` **不传 `excluded`**。故障转移重选时，组可能再次选到成员映射的同一失败渠道 → 外层 candidates 排除后 `ErrNoCandidates`，提前终止；应把 excluded 透传进组内选择。

### P1-4 `Resolver.ensureState()` 数据竞争
`selector.go:71-85` 无锁懒初始化 `r.state`；`snapshot()`（值接收者，`selector.go:108`）无锁读 `r.state`。生产场景：`OnConfigChange` API 处理器并发触发 `UpdateSnapshot`，同时网关 `Resolve` 在读 —— data race，且两个并发 `UpdateSnapshot` 都会各自 new 一个 state，**先提交的快照会被静默丢弃**（路由表回退）。修复：构造时即初始化 state，或在 Resolver 内加 `sync.Once`/互斥保护 state 指针本身。本报告无法跑 `-race`，但按代码路径可确定可触发。

### P1-5 签到主链路不走渠道代理（身份束"同一出口"承诺破裂一半）
`base.go:272` `CallWithAuth.doReq` 直接用 `b.Client`，**不调用** `clientForChannel`；而同文件 `RefreshAccessToken`（:227）与 `FetchStatusQuotaPerUnit`（:330）却用 `clientForChannel` 走 `ch.ProxyURL`——同一适配器内出口行为自相矛盾。另 `browser/executor.go:117-135` 启动浏览器未注入 `--proxy-server`，CDP 签到浏览器流量直连本地 IP。web 身份束视图文案声称"签到浏览器、声明式签到、网关上游、健康探测共用同一出口/UA/时区"——目前只有网关+token 刷新部分成立。修复：`doReq` 内统一 `clientForChannel`，executor 按 channel 注入代理与 UA。

### P1-6 Generic/Declarative 适配器把 CredentialRef 当明文 Bearer 直发上游
`generic.go:58-59`：`req.Header.Set("Authorization", "Bearer "+channel.CredentialRef)`；`declarative.go:167-168` 同样。`CredentialRef` 是密钥库引用串而非令牌——这与 `wiring.go:144` 注释自述的历史缺陷（旧 AUDIT P1-9）同类。后果：generic 渠道走适配器的 `Models()/Health()` 恒 401。修复：注入 `SecretResolver` 后解析再发。注：`fetchModels`/`channelTest`/`syncChannelModels`（API 层）走的是密钥库解析路径，正确。

### P1-7 `channelTest` 缺 `s.Repo == nil` 防御 —— 裸 Server 下 panic
`server.go:1273` 直接 `s.Repo.GetChannel(...)`；同类处理器（channelStats/channelKeys/channelDuplicate…）都有 nil guard 返回 503。`NewServer()` 构造的实例（无持久层）被调 `POST /api/v1/channels/test` 会 panic（http.Server 恢复连接但无错误信封）。一致性修复即可。

### P1-8 Export/Import 不覆盖 ProviderModel / ModelGroup(+members) / ChannelKey —— 配置迁移丢绑定
`export.go:20-46` 只导出 providers/channels/models/routes；`import.go` 也只导入这 4 类。导入全新实例后**所有 provider-model 绑定、模型组、渠道多 key 全部丢失**，网关对所有模型 `ErrNoCandidates`；且仅用 channel-keys 的渠道连凭据引用都没了（key 的 secret_ref 指向的密文虽在 include_secrets 包内，但 key 元数据未导出）。一个自称"配置可移植"的功能迁移后是残的。修复：PackageData 加三 sections（版本升到 2，兼容读取 v1）。

### P1-9 Runaway Guard 从未接入热路径 + 若接入则内存无界增长
`gateway.Config.Guard`（`gateway.go:186`）在整个 `ServeHTTP` 中**从未被读取**；`wiring.go:286` 照常 `guard.New()` 注入。STATUS 声称"已接线"不实——重复 payload 熔断功能目前不存在。另外 `guard.runaway.go` 的 `sessions` map 只在 `Trip` 被调用时按 session 惰性清理，空 session 键永不删除，真接入后是慢速内存泄漏，需加全局容量/定期清扫。

### P1-10 `syncChannelModels` 重建绑定非原子 + 全表预取
`server.go:660-686`：`ListProviderModels(ctx, "")` 取**全部渠道**绑定后内存过滤、逐条 DELETE、再逐条 CreateModel（错误 `_ =` 吞掉）+ CreateProviderModel。中途失败留下半新半旧绑定集。修复：`WithTx` 包裹 + repo 提供 `DeleteProviderModelsByChannel`；`CreateModel` 改幂等 upsert 或显式忽略已存在错误。

### P1-11 `resolveChannelCredential` 静默吞错返回空凭据
`wiring.go:364-369`：选定 key 的 `secStore.Get` 失败 → 落到 `CredentialRef` 分支；再失败 → `return "", "", nil`（**nil error**）。网关随后发出**无认证头**的请求 → 上游 401，运维侧无法区分"上游拒绝"与"本地密钥丢失"。修复：解析失败必须返回 error，让网关以 503/配置错误快速失败。

## 5. P3 — 规范化 / 死代码 / 工程一致性

1. **死代码**：`extras.go` 全文件 281 行（P0-1 的载体）；`internal/config` 包 `Load()` 及 JSON 配置文件支持**无人调用**（cmd 用自己的 `defaultDataDir()`，且 `RELAYHUB_DATA_DIR` 在 cmd 路径不被读取）——要么接入 cmd，要么删除避免"配置了却不生效"的陷阱；`config.Config.DatabasePath/BackupDir` 等字段在 `app.Config`/`wiring.go` 无对应消费（wiring 硬编码 `filepath.Join(DataDir, "relayhub.db")`）。

## 6. 安全附注（未发现高危注入/越权，但以下需正视）

1. **导出包"防篡改"校验名不符实**：`export/format.go:59-67` 校验和 = 明文 sha256（无密钥）。攻击者改包后重算 checksum 即可通过 `PreviewPackage`/`ApplyWithOptions`。`ErrTamperedPackage` 的措辞与 `docs/security.md` 的暗示高估了保护力度。含密钥导出时应用密码派生 HMAC；不含时文档降级为"防传输损坏"。
2. **代理凭据非常量时间比较**：`http_proxy.go:112`、`socks5_proxy.go:170` 用 `==` 比对 Basic/用户名密码（管理面 `subtleEqual` 已做恒定时间，口径应统一）。本地回环下风险低，但配置了对外的部署形态时是时序侧信道。
3. **外呼端点**：`identity.ProbeEgress` 硬编码 `https://api.ipify.org`（PATCH identity 带 `probe=1` 时）——"本地优先"产品的隐私面需在设置里明示并提供关闭。
4. **本地信任模型仍是"回环即授信"**：`authorize()`（server.go:455-459）在 `LocalOnly && Token==""` 时对所有回环进程放行（GET 尤其宽松）；`browserBoundary` 已挡浏览器跨站，这是好设计，但本机任意进程仍可调用全部管理写接口+读取渠道配置。文档 `docs/security.md` 应明示该威胁模型（桌面场景可接受，团队共享机不可接受）。
5. **正向安全实践（值得保持）**：密钥 AES-256-GCM 且 ref 绑定 AAD 防密文搬家；`FileKeyProvider` 0600/拒绝符号链接/拒绝宽权限；`SQLKeyBackend` 只存 SHA-256 摘要；`browserBoundary` 对 Host/Sec-Fetch-Site/Origin 的严格校验；`decodeJSON` 禁未知字段+单值校验+1MB 上限；管理面强制 loopback + 远程模式强制 token+allowlist+限流的 fail-closed 校验；代理目标策略默认 LocalOnly、开公网需显式 Open；DNS 解析后直接以解析结果 IP 拨号（消除 rebinding TOCTOU）；运行时下载强制 pinned SHA-256；CLI 同步备份-原子写-校验-回滚闭环；签到"persistence_failed 先核对再重试"的保守语义。
